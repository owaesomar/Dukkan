# Authorization

Authorization is deny-by-default. Authentication produces a user principal; it does not grant access to stores. Private store routes resolve an active store and active `(store_id, user_id)` membership, then check the permission required by the action. Missing membership returns 404 to avoid disclosing store existence; insufficient permission for an existing membership returns 403. Store lists are joined through active memberships, and mutations use CSRF protection.

Roles grant bounded capabilities: `owner` has full store permissions; `admin` has full store permissions except it cannot grant owner/admin; `manager` can read members, manage catalog/inventory, fulfill orders, read analytics and subscription information; `catalog` manages catalog/inventory; `fulfillment` can read inventory and fulfill orders; `staff` can read and fulfill orders; `viewer` has read access. Subscription changes and membership mutations are limited to owners/admins. Membership changes lock the store row, re-check the actor's current grant, and preserve at least one active owner.

Platform access uses the separate `platform_admin_roles` table and a dedicated dependency. Store membership never implies platform access. Bootstrap the first grant for an existing account with `cd backend && uv run python -m app.modules.platform_admin.bootstrap admin@example.com`; subsequent grants and revocations require an existing platform admin. Admin actions such as merchant status changes, store suspension, plan changes, and global role grants are recorded in the platform audit log.
